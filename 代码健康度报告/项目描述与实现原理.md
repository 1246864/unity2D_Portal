# Unity 2D Portal 项目描述、实现细节与原理解析

## 1. 项目描述

### 1.1 一句话介绍

这是一个基于 **Unity 2022.3、URP 2D Renderer 和 C#** 开发的二维平台跳跃与双门传送原型：玩家可以进行具有加速度、土狼时间、跳跃缓冲和可变跳高的平台移动，并通过两扇可旋转传送门完成位置、速度、角色显示姿态和相机空间的连续迁移，同时在门内看到另一扇门附近的实时场景画面。

### 1.2 项目定位

项目重点不是制作完整关卡或商业美术，而是验证一组彼此关联的技术问题：

1. 2D 平台角色的移动手感与斜坡适配；
2. 双门之间的位置、切线偏移和速度变换；
3. 传送门画面的相机捕获、交叉显示、半屏重建与遮罩裁剪；
4. 玩家显示旋转与物理胶囊分离；
5. 传送后的相机相对矩阵映射、投影镜像与输入反转；
6. 门洞经过 Tilemap 地形时的动态碰撞开洞与恢复；
7. 通过 PlayMode 测试验证真实物理和组件协作。

因此，它更接近一个 **“2D 平台控制器 + 传送门技术验证框架”**，后续可以继续扩展为解谜平台游戏。

### 1.3 技术栈

| 类别 | 技术 |
|---|---|
| 引擎 | Unity 2022.3.61f1c1 |
| 渲染 | URP 14.0.6、2D Renderer、Camera、RenderTexture、SpriteMask |
| 语言 | C# |
| 物理 | Rigidbody2D、CapsuleCollider2D、CircleCollider2D、TilemapCollider2D、CompositeCollider2D |
| 地图 | Unity Tilemap、运行时生成 Tile/Sprite |
| 测试 | Unity Test Framework、NUnit、PlayMode 集成测试 |
| 自定义渲染 | PortalHintBeam Shader，加法混合、噪音、流光和呼吸效果 |
| 辅助工具 | Python + Pillow 生成占位美术 |

### 1.4 当前主要功能

- 地面/空中分别设置加速度和减速度；
- 按目标跳高计算起跳速度；
- 土狼时间、跳跃缓冲、松开跳跃键截断上升；
- 下落额外重力、最大下落速度和坠落重生；
- 45° Tilemap 斜坡行走；
- 双门配对、开门动画、冷却和连续传送；
- 门可旋转，出口位置和速度按门的局部坐标系计算；
- 玩家物理根节点保持竖直，显示节点负责旋转和回正；
- 相机位置与角度独立平滑跟随，支持前瞻和传送后连续映射；
- 同向门传送后切换相机水平镜像和水平输入方向；
- A/B 门户相机交叉捕获，生成对方门的 Portal View；
- 完整图像重建为半屏 Sprite，再通过上下 SpriteMask 形成门洞显示区域；
- 门后地形碰撞动态开洞，门移动或关闭后恢复；
- 根据 Tilemap 邻居关系自动生成内描边；
- 静态光带和粒子提示门的开口方向。

## 3. 玩家控制器：手感与物理稳定性

## 3.1 物理根节点与显示节点分离

传送门要求玩家离开时产生旋转效果，但如果直接旋转 Rigidbody2D 和胶囊碰撞体，可能导致：

- 胶囊与地面的接触形状突然变化；
- 斜坡上出现不稳定碰撞；
- 旋转后的碰撞体插入门或地形；
- 后续平台移动难以继续使用竖直胶囊假设。

当前方案将“物理身份”和“视觉姿态”分开：

- **物理根节点**：保存 Rigidbody2D、CapsuleCollider2D 和 Center Point，保持物理规则稳定；
- **Player Visual**：负责显示旋转、传送后的姿态以及逐渐回正；
- **相机**：参考 Visual 的姿态计算画面角度，而不是直接驱动物理碰撞体旋转。

**核心原理：视觉可以旋转，物理不必跟着旋转。** 这是用视觉表现模拟空间转换，同时保持 2D 平台控制器确定性的关键取舍。

## 3.2 水平移动与加减速

控制器不是直接把水平速度设置为输入值，而是使用：

```text
targetSpeed = moveInput × moveSpeed
velocity.x  = MoveTowards(velocity.x, targetSpeed, acceleration × fixedDeltaTime)
```

地面和空中分别使用不同参数：

- 地面有输入：较高加速度，保证响应；
- 地面无输入：较高减速度，快速停稳；
- 空中有输入：较弱加速度，保留空中调整能力；
- 空中无输入：较弱减速度，避免跳跃轨迹突然僵硬。

这比单纯设置 `velocity.x = input × speed` 更容易同时获得“起步不突兀”和“转向够灵敏”的手感。

## 3.3 按目标跳高反推起跳速度

在匀减速上升模型中：

```text
v² = 2gh
```

因此：

```text
v = sqrt(2g × jumpHeight)
```

代码还加入半物理步重力补偿：

```text
launchVelocity = sqrt(2g × jumpHeight) + 0.5g × fixedDeltaTime
```

对应实现见 [PlayerController2D.cs:339-349](../Assets/Scripts/PlayerController2D.cs#L339-L349)。

半帧补偿用于减小离散积分造成的顶点误差，使实际跳高更接近配置的 6 格。这里的有效重力来自 `Physics2D.gravity.y × Rigidbody2D.gravityScale` 的绝对值。

## 3.4 土狼时间与跳跃缓冲

两者解决的是不同的输入时序问题：

- **土狼时间**：玩家刚离开平台的一小段时间内，仍允许起跳；
- **跳跃缓冲**：玩家稍早按跳跃、随后落地时，仍能在落地后立即起跳。

每个 FixedUpdate 更新两个计数器：

```text
离开地面后：coyoteCounter 逐渐下降
按下跳跃后：jumpBufferCounter 逐渐下降

jumpBufferCounter > 0 且 coyoteCounter > 0
    → 执行跳跃并清空两个计数器
```

这样可以把“玩家认为应该跳”与“物理引擎严格同帧接触”之间的差异转化为可控手感。

## 3.5 可变跳高与下落控制

- 松开跳跃键时截断上升速度，实现短按小跳、长按大跳；
- 下落时施加额外重力，使下落比上升更利落；
- 限制最大下落速度，避免高速下坠导致碰撞不稳定；
- 低于 `fallLimitY` 后回到出生点。

这些机制共同构成平台游戏常用的“上升可控、下落明确”的跳跃曲线。

## 3.6 斜坡速度映射

控制器没有依赖摩擦力把玩家推上斜坡，而是把水平速度映射为沿坡速度。

代码根据地面法线计算坡面升降率：

```text
slopeRise = -groundNormal.x / groundNormal.y
velocity.y = velocity.x × slopeRise
```

见 [PlayerController2D.cs:323-336](../Assets/Scripts/PlayerController2D.cs#L323-L336)。

例如向右走上 45° 上坡时，水平速度会转换为相应的向上分量；下坡则产生向下分量，使胶囊更贴合坡面。平地上则主动清零由该控制器管理的垂直分量，避免上一块坡面的速度被带到下一块平台。

## 4. 传送门：位置、速度与旋转的坐标变换

## 4.1 为什么必须使用门的局部坐标系

如果使用世界坐标直接处理出口，例如“保留世界 Y 高度、把 X 速度反向”，门一旦旋转就会出现问题：

- 世界 Y 不再等于门的高度方向；
- 世界 X 不再等于门的开口方向；
- 玩家可能被放到门内或门后；
- 出门速度方向与视觉空间不一致。

因此，当前实现把每扇门看成一个局部二维坐标系：

- **切线**：`transform.up`，沿门洞高度方向；
- **法线**：`OpeningDirection`，指向门的开口一侧；
- **背面方向**：`-OpeningDirection`。

门旋转时，这些向量随 Transform 一起旋转，后续计算不需要为某个固定角度写特殊分支。

## 4.2 碰撞触发：身体与 Center Point 分工

门碰撞箱放在 Snapshot 专用层：

- 玩家身体胶囊通过 `excludeLayers` 忽略该层，避免把薄门碰撞箱当成墙；
- 玩家中心的 CircleCollider2D 与门碰撞箱发生碰撞；
- `PortalPair.OnGateHit` 只接受 `collision.collider == controller.CenterPoint`。

**原理：身体负责地形物理，中心点负责传送语义。** 这可以避免胶囊边缘擦到门就过早触发，也避免通过 `Physics2D.IgnoreCollision` 在碰撞箱重新启用后丢失忽略状态。

## 4.3 出口位置计算

入口处的玩家相对位置被投影到入口门切线上：

```text
tangentOffset = Dot(playerPosition - sourceCenter, sourceTangent)
```

出口位置由三部分组成：

```text
target = partnerCenter
       + exitDirection × front
       + partnerTangent × tangentOffset
```

其中：

```text
front = gateThickness / 2 + centerPointRadius + exitMargin
exitDirection = partner.OpeningDirection
```

对应实现见 [PortalPair.cs:298-311](../Assets/Scripts/PortalPair.cs#L298-L311)。

这个公式同时完成两件事：

1. **保留沿门方向的相对位置**：从入口门上端附近进入，就从出口门对应的上端附近离开；
2. **沿出口法线离开门面**：确保中心点落在碰撞箱外侧，并留出半径和额外间距，降低刚出门就再次碰撞的概率。

## 4.4 速度变换

进入门时，速度被分解到入口门的法线和切线上：

```text
normalSpeed  = Dot(velocity, sourceNormal)
tangentSpeed = Dot(velocity, sourceTangent)
```

出门时重新组合：

```text
exitVelocity = partnerNormal × (-normalSpeed)
             + partnerTangent × tangentSpeed
```

见 [PortalPair.cs:394-411](../Assets/Scripts/PortalPair.cs#L394-L411)。

其物理含义是：

- 穿过门面后，原来的“向前穿门”变为“向出口外侧离开”，所以法线分量反向；
- 沿门洞切线方向的运动不因穿门而消失，所以切线分量保留；
- 因为使用两门各自的局部向量，旋转门会自动改变最终世界速度方向。

**注意：** 这里的“切线保留”指入口切线系数被重新表达在出口切线上，并不是直接保留世界坐标中的速度向量。

## 4.5 玩家显示旋转

当前实现根据两门 `transform.up` 的世界角度差计算出口角：

```text
exitAngle = partnerAngle - sourceAngle
```

随后只旋转 Visual，并按 `portalRealignSpeed` 和回正曲线逐渐恢复竖直。物理胶囊不随 Visual 旋转。

这种设计让玩家在出门瞬间获得空间方向变化的视觉反馈，同时避免长期保持倾斜胶囊破坏平台控制。

当前公式建立在“进门时玩家显示已竖直”的假设上；如果上一次传送尚未回正就再次传送，需要进一步定义连续传送的角度叠加规则。

## 4.6 冷却与强制捕获

一对门共享传送冷却，避免玩家刚离开出口就被同一帧或下一帧立即传回。

传送后还会：

- 重置门的开门动画状态；
- 设置强制捕获标记；
- 在后续 LateUpdate 中刷新 A/B 捕获和半屏画面。

**原理：位置、相机和画面不能各自随意更新。** 传送是一个跨物理、视觉和渲染的事务，需要明确更新顺序。

## 5. Portal View：门内实时画面的生成原理

## 5.1 从相机到 Sprite

每扇门包含 Portal Camera 和 RegionSnapshotCamera，基本链路为：

```text
Portal Camera 渲染场景
    ↓
RenderTexture
    ↓
Texture2D.ReadPixels
    ↓
Texture2D.Apply
    ↓
完整 Sprite
    ↓
半屏 Sprite + Portal View Transform 对齐
```

[RegionSnapshotCamera.cs](../Assets/Scripts/RegionSnapshotCamera.cs) 负责渲染和资源创建，[CaptureDisplayGroup.cs](../Assets/Scripts/CaptureDisplayGroup.cs) 负责输出关系和最终显示。

尺寸不变时会复用纹理资源，避免把“每帧更新图像”变成“每帧重建全部 Unity 对象”。

## 5.2 A/B 交叉输出

配对完成后，捕获输出交叉连接：

```text
A.capture.output = B.output
B.capture.output = A.output
```

见 [CaptureDisplayGroup.cs:896-901](../Assets/Scripts/CaptureDisplayGroup.cs#L896-L901)。

因此，A 相机生成的画面最终显示在 B 的 Portal View 上，B 相机的画面显示在 A 上。玩家看向任意一扇门时，看到的是另一扇门附近的空间，而不是本门相机的简单复制。

## 5.3 为什么要重建半屏 Sprite

当前 Portal View 使用捕获纹理的一半。实现不是简单把完整 Sprite 缩放到一半，而是：

1. 始终保存完整捕获 Sprite；
2. 根据左半或右半的 Rect 创建半屏 Sprite；
3. 按完整画面中的位置调整 Portal View 的 X；
4. 保留 View Center 和输出对象的 Z 关系。

如果以已经裁过的半屏继续裁剪，第二次切换就会丢失原始图像范围。因此“完整 Sprite 是源，半屏 Sprite 是派生结果”是这一实现的重要不变量。

## 5.4 SpriteMask 如何形成门洞

Portal View 使用 `VisibleOutsideMask`，上下两块大遮罩覆盖门洞之外的大部分区域，中间只留下随开门进度变化的带状空间。

```text
开门进度 0：上下遮罩接近中线，门洞接近关闭
开门进度 1：上下遮罩移动到配置偏移，露出完整门洞高度
```

遮罩还会根据玩家眼睛位置调整朝向，使显示区域尽量正对观察者。输出与遮罩使用专用排序层和自定义遮罩范围，避免 A 门遮罩错误影响 B 门。

## 5.5 防止递归捕获

Portal View 位于 Snapshot 专用层：

- Portal Camera 的 Culling Mask 排除 Portal View 所在层，避免拍到输出画面形成“相机拍屏幕、屏幕再显示相机”的递归；
- 主相机仍渲染 Snapshot 层，因此玩家可以看到最终 Portal View；
- 玩家身体对该层的碰撞排除是物理过滤，渲染 Culling Mask 是视觉过滤，两者目的不同。

## 5.6 静态与动态捕获范围

捕获范围由 PortalPair 统一下发：

- **静态模式**：使用固定 `captureWidth × captureHeight`；
- **动态模式**：

```text
worldHeight = 主相机 orthographicSize × 2 × cameraSizeMultiplier.y
worldWidth  = 主相机可见宽度 × cameraSizeMultiplier.x
```

随后按 PPU 计算纹理像素尺寸，并设置捕获相机的 orthographicSize 和 aspect。

**原理：世界尺寸决定“拍到多少空间”，PPU 决定“用多少像素表达这些空间”。** 两者必须保持统一比例，否则 Portal View 会出现缩放或错位。

## 6. 相机跟随、空间连续性与镜像

## 6.1 常规跟随

CameraFollow2D 支持：

- 位置 SmoothDamp；
- 角度独立平滑；
- 根据局部水平速度进行前瞻；
- 玩家回正时调整相机角速度；
- 瞬移时 SnapToTarget，避免相机从旧位置缓慢飞过整张地图。

位置和角度分开平滑，是因为“相机应该快速跟上位置”和“画面旋转不应太突然”通常需要不同节奏。

## 6.2 传送时保存完整相对变换

传送前记录相机在玩家 Visual 空间下的相对矩阵：

```text
cameraRelative = playerVisual.worldToLocalMatrix
               × camera.localToWorldMatrix
```

这个矩阵包含相机相对玩家的：

- 位置；
- 旋转；
- 缩放。

传送后，玩家 Visual 已移动并旋转，再将相对矩阵映射回世界空间：

```text
newCameraWorld = newPlayerVisual.localToWorldMatrix
               × cameraRelative
```

**核心原理：传送不是把相机移动到某个固定偏移，而是保持“相机相对玩家的整个坐标关系”。** 因此，原有前瞻、视角和画面构图可以在新空间中延续。

## 6.3 为什么延迟到 LateUpdate

碰撞回调发生时，玩家、刚体、Visual 和其他脚本可能还没有完成本帧更新。如果立即写入相机位置，后续逻辑可能再次覆盖它。

CameraFollow2D 先保存 pending relative matrix，到 LateUpdate 等玩家最终位置确定后再应用。这样把执行顺序变成：

```text
物理碰撞 → 玩家传送 → 本帧其他更新 → 相机相对映射 → 捕获/显示
```

延迟不是为了让动画更平滑，而是为了消除帧内更新顺序竞争。

## 6.4 同向门传送后的投影镜像

当两门逻辑 Facing 相同，传送后的视觉空间需要额外水平翻转。当前实现分三部分：

1. `PlayerCameraMirror` 每帧先恢复原始投影矩阵；
2. 如果镜像开启，将 `projectionMatrix.m00` 取反；
3. 同步切换玩家水平输入，并镜像相机的待应用相对位置。

投影矩阵 `m00` 控制水平方向的投影缩放，取反后画面左右翻转。每帧先 Reset 再按状态设置，可以避免在已翻转矩阵上反复取反造成奇偶状态漂移。

输入同步反转的原因在于：玩家看到的左右方向已经改变，如果输入仍按原世界方向解释，操作感会与视觉反馈相反。

**需要注意：镜像不是简单设置 SpriteRenderer.flipX。** 它同时涉及整个相机画面、玩家控制和相机位置，是一个统一的观察空间变换。

## 7. Tilemap 地形动态开洞

## 7.1 问题来源

门视觉上打开后，如果背后的 Tilemap 碰撞仍然完整，玩家会被一面“看不见的地形墙”挡住，无法真正穿过门洞。

但如果直接删除 Tile：

- 会改变美术；
- 恢复时更复杂；
- 可能影响 Outline 和其他地图逻辑。

当前方案只修改碰撞，不删除视觉 Tile。

## 7.2 开洞流程

```text
收集两扇门的开洞矩形
    ↓
找到矩形覆盖的 Tilemap 格子
    ↓
读取每格原有 ColliderType 和物理形状
    ↓
门洞矩形与格子物理多边形做布尔差
    ├─ 完全在洞内：暂时禁用该格碰撞
    ├─ 部分相交：生成残余 PolygonCollider2D
    └─ 不相交：保持原状
    ↓
重建 CompositeCollider2D
    ↓
Physics2D.SyncTransforms
```

矩形包含门洞高度、向门背面延伸的宽度以及少量前缘边距，使门前后碰撞过渡更可靠。

## 7.3 为什么需要残余 PolygonCollider2D

一个 Tile 可能只有一部分被门洞覆盖。若简单禁用整格碰撞，会把门洞外的地形也删掉，形成过大的空洞。

布尔差保留未覆盖区域，并用新的 PolygonCollider2D 表示残余部分。这样门洞边缘可以贴近实际矩形，而不是只能按整格粗细切割。

## 7.4 移动、旋转与恢复

当门洞矩形变化时：

1. 恢复上一轮所有被修改的 Tile 和残余碰撞；
2. 清空旧矩形记录；
3. 按最新门位置重新切割；
4. 重建 CompositeCollider2D。

组件禁用或销毁时也会恢复原 ColliderType 并销毁运行时残余对象。

**核心不变量：任何新洞生成之前，旧洞必须能够完整恢复。** 否则门移动几次后，地图会留下不可逆的碰撞碎片。

## 8. Tilemap 内描边与门位置提示

## 8.1 邻居位掩码生成描边

TilemapOutline 对每个实心格检查四个方向的邻居：

- 某方向没有 Tile，说明该方向是地形边缘；
- 深色地形与相邻非深色地形之间，也可以形成材质边界；
- 四个方向组成 4 bit 掩码，共 16 种组合；
- 每种组合对应一张预生成的内描边 Tile。

```text
上 / 下 / 左 / 右邻居状态
          ↓
       4 bit mask
          ↓
    选择对应描边 Sprite
```

描边绘制在独立 Outline Tilemap 中，不修改原始地形 Tile，因此视觉生成与碰撞地形保持分离。

斜坡不能使用普通水平/垂直边缘规则，当前另外生成四种方向的斜边 Tile。

## 8.2 光带与粒子

Portal Hint 使用场景中的静态 SpriteRenderer 和 ParticleSystem，运行时主要更新材质和参数：

- A/B 使用不同颜色；
- 加法混合形成高亮；
- 噪音扰动避免光带过于机械；
- 流光参数提供方向感；
- 呼吸频率控制亮度节奏；
- 粒子速度根据 FacingSign 调整。

把光带对象保留在场景中，可以避免每次开关门都创建 GameObject；运行时的职责主要是驱动效果，而不是反复搭建对象树。

---

## 9. 一帧中的关键执行顺序

理解本项目，最重要的是理解物理、视觉和渲染并不是同一个更新阶段：

```text
Update
├─ 读取输入
├─ 更新开门等常规逻辑
└─ 下发捕获尺寸和开洞配置

FixedUpdate / 物理回调
├─ 地面检测、移动、跳跃和重力
├─ Center Point 撞门
├─ 计算并执行玩家传送
└─ 记录相机 pending 相对矩阵、冷却和强制捕获

LateUpdate
├─ 玩家最终 Transform 已确定
├─ 应用相机 pending 相对矩阵
├─ 执行常规相机跟随/回正
├─ 设置投影镜像
├─ 必要时刷新 Portal Camera
├─ 更新半屏 Sprite 和遮罩
└─ 更新地形开洞与光带参数
```

这套顺序的目标是避免：

- 相机先跟随旧玩家位置，随后玩家才传送；
- 捕获先于出口状态更新，导致画面晚一帧；
- 物理回调中反复修改 Transform，产生同步时序问题；
- 遮罩和 Sprite 在不同阶段分别使用不同门状态。

## 10. 测试与验证方式

当前源码包含 **4 个 PlayMode 测试文件、23 个 `[UnityTest]`**，覆盖：

| 领域 | 验证内容 |
|---|---|
| 玩家物理 | 地面站立、6 格跳、水平移动、坠落重生、斜坡 |
| 相机 | 常规跟随、传送旋转与回正 |
| 传送门 | 门洞、开门动画、重新启用、传送、淡出、光带和背面隐藏 |
| Portal View | View 结构、半屏 API、专用层、静态/动态捕获尺寸 |
| Tilemap | 地形碰撞、Outline、Tilemap 斜坡 |
| 地形开洞 | 开洞/恢复、旋转向量、门移动后的旧洞恢复 |

这些测试以结构、数值和真实物理结果为主。它们能验证“组件是否按预期协作”，但不能完全证明：

- 最终 Portal View 像素和 SpriteMask 一定正确；
- Player 构建后 Shader 一定被保留；
- 同向门连续镜像的所有奇偶情况都正确；
- 双门每帧捕获满足目标设备性能预算。

历史测试 XML 曾记录 23/23 通过，但其时间早于当前镜像提交，因此最新代码仍应重新运行完整测试并补充镜像、构建和视觉验证。

## 11. 设计亮点与技术难点

### 11.1 设计亮点

1. **传送不是简单改位置**：同时处理切线偏移、速度、显示姿态和相机关系。
2. **物理与视觉解耦**：保留稳定胶囊，同时允许玩家和画面产生空间旋转。
3. **使用局部坐标系支持旋转门**：不为 45°、90° 等角度写固定分支。
4. **相机采用完整相对矩阵**：保留位置、旋转和缩放，而不是只保存一个 Vector3 偏移。
5. **Portal View 交叉输出**：A/B 捕获和显示关系清晰，可形成真正的双门观察效果。
6. **地形只切碰撞不切美术**：门洞不影响原始 Tilemap 视觉，且支持恢复。
7. **Center Point 与身体分工**：分别服务传送判定和地形物理，减少误触发。
8. **具备真实 PlayMode 回归**：测试直接驱动 Unity 物理和场景，而不是只测孤立数学函数。

### 11.2 主要技术难点

- 多脚本在同一帧内的执行顺序；
- 两门旋转后法线、切线和速度方向的一致性；
- 相机镜像、输入方向和玩家视觉方向的统一；
- 捕获纹理尺寸、PPU、半屏 Sprite 和世界坐标之间的比例关系；
- 遮罩排序层、Culling Mask 和 Snapshot 层之间的隔离；
- 地形布尔切割后的恢复与 CompositeCollider2D 重建；
- GPU 图像回读的性能与纹理资源生命周期。

---

## 12. 当前实现边界与工程取舍

本项目当前优先验证“功能能否成立”，因此保留了一些明确的原型取舍：

1. Portal Camera 默认每帧捕获并同步 ReadPixels，实现直接，但需要进一步优化性能。
2. Portal View 测试主要验证结构，最终像素仍需视觉验收。
3. PortalHintBeam 通过 Shader.Find 使用，Player 构建保留需要明确引用和构建验证。
4. 连续传送时玩家尚未回正的角度规则需要进一步明确。
5. ProjectBuilder 已落后于手工维护的主场景，不应直接执行 Rebuild。
6. 主场景当前以手工配置为主，场景、文档和测试基线需要同步维护。
7. 地形开洞主要面向当前标准 Tilemap/Grid 结构，不等同于任意 TileBase 和任意变换的通用解决方案。

这些边界不妨碍它作为技术原型展示，但在扩展关卡或发布前，应先完成对应测试、性能和生命周期治理。

## 13. 可用于项目首页的精简介绍

> **Unity 2D Portal** 是一个基于 Unity 2022.3 与 URP 2D Renderer 的二维平台跳跃和双门传送技术原型。项目实现了带加速度、土狼时间、跳跃缓冲、可变跳高和斜坡适配的平台控制器，并围绕可旋转双门构建了完整的传送链路：根据入口/出口局部坐标计算玩家位置与速度，使用物理根节点和显示节点分离保持碰撞稳定，通过相对矩阵迁移相机空间，并在同向门场景下同步处理投影镜像和输入方向。
>
> 门内画面由 A/B Portal Camera 交叉捕获，经 RenderTexture、Texture2D 和半屏 Sprite 重建后显示在对方门内，再通过 SpriteMask 和开门动画形成动态门洞。针对 Tilemap 地形，项目还实现了仅修改碰撞的门洞布尔切割、残余多边形生成和完整恢复机制。项目包含 23 个 PlayMode 用例，为玩家物理、传送、Portal View 和地形开洞提供回归基础。

---

## 14. 总结

这个项目的核心不是某一个单独脚本，而是三套空间的协同：

```text
物理空间：Rigidbody2D、胶囊、Center Point、Tilemap 碰撞
视觉空间：Player Visual、Portal View、SpriteMask、光带和粒子
观察空间：主相机、Portal Camera、相对矩阵、投影镜像和输入方向
```

- 传送门数学负责把运动从入口空间变换到出口空间；
- 玩家物理/显示分离负责让空间变化不破坏平台控制；
- Portal View 负责让另一处空间可见；
- 相机相对映射和镜像负责让观察关系保持连续；
- 地形开洞负责让视觉上的通道在物理上真实存在。

只有这几部分在同一帧内按正确顺序协作，传送才不仅是“坐标瞬移”，而会形成位置、速度、画面和操作感受都连续的空间穿越效果。
