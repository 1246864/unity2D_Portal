## 2. 项目架构与运行关系

### 2.1 程序集边界

```text
Platformer.Runtime
├─ PlayerController2D
├─ CameraFollow2D / PlayerCameraMirror
├─ PortalPair
├─ CaptureDisplayGroup
├─ RegionSnapshotCamera
├─ PortalTerrainCarver
└─ TilemapOutline

Platformer.Editor
└─ ProjectBuilder / PlayerController2DEditor

Platformer.PlayTests
└─ 引用 Runtime，使用 Unity Test Framework / NUnit
```

三个程序集职责划分清楚，Editor 仅面向编辑器平台，PlayTests 引用 Runtime，属于项目的结构性优点。

### 2.2 核心运行时数据流

```text
键盘 / 测试输入
    ↓
PlayerController2D
    ├─ Rigidbody2D 水平移动、跳跃、重力、重生
    └─ Player Visual 显示旋转与传送后回正

Portal Gate 碰撞
    ↓ CaptureDisplayGroup 转发
PortalPair.OnGateHit
    ├─ 检查玩家 Center Point、配对和冷却
    ├─ 计算出口位置、切线偏移和速度变换
    ├─ PlayerController2D.TeleportWithPortalRotation
    ├─ CameraFollow2D.TeleportRelative
    ├─ 同向门时 PlayerCameraMirror + 输入反转 + 相机位置镜像
    └─ 强制刷新两扇门捕获

主相机 / 场景
    ↓ Portal Camera 渲染
RenderTexture
    ↓ Texture2D.ReadPixels + Apply
完整 Sprite
    ↓ CaptureDisplayGroup 半屏 Sprite、位置偏移、SpriteMask
另一扇门的 Portal View

PortalPair
    ↓ 门状态与开洞矩形
PortalTerrainCarver
    ├─ 暂时修改 Tile 碰撞类型
    ├─ 生成残余 PolygonCollider2D
    ├─ 重建 CompositeCollider2D
    └─ 停用时恢复原碰撞

Terrain Tilemap
    ↓ 邻居、资源名称和斜坡规则
TilemapOutline
    └─ 运行时生成 Outline Tilemap、Sprite 和 Tile
```

### 2.3 耦合集中点

- [CaptureDisplayGroup.cs](../Assets/Scripts/CaptureDisplayGroup.cs) 约 1083 行，同时负责配对、View 解析、朝向、半屏裁剪、遮罩、开门动画、淡出、光带、粒子和碰撞转发，是最大的修改集中点。
- [PortalPair.cs](../Assets/Scripts/PortalPair.cs) 约 494 行，是传送、相机、输入镜像和地形开洞的业务协调中心。
- [ProjectBuilder.cs](../Assets/Editor/ProjectBuilder.cs) 约 863 行，同时负责导入、资源生成、场景重建、校验和预览，且已明显落后于当前场景。

这三处是后续回归测试和拆分时最应优先保护/治理的位置。

## 5. P0 / P1 详细发现

### H-01 — Rebuild 创建 A 门时存在确定的空引用调用链

**证据：**

1. `facing` 默认是 `Right`，属性 setter 在值变化时立即调用 `ChangeFacing()`：[CaptureDisplayGroup.cs:118-132](../Assets/Scripts/CaptureDisplayGroup.cs#L118-L132)。
2. Builder 在 [ProjectBuilder.cs:639-647](../Assets/Editor/ProjectBuilder.cs#L639-L647) 中先添加组件、设置 A 门为 `Left`，然后才赋值 `capture/output/viewCenter/maskTop/maskBottom`。
3. A 门左分支立即访问 `maskTop.transform`、`viewCenter.localScale`、`output.flipY` 和 `PartnerOutput`：[CaptureDisplayGroup.cs:436-461](../Assets/Scripts/CaptureDisplayGroup.cs#L436-L461)。

**结论：** 对新建的默认 Right 组件执行 A→Left 时，依赖字段尚未连接，`maskTop` 等引用为空，控制流可触发 `NullReferenceException`。这是静态调用链结论，本次未实际执行菜单。

**影响：** Rebuild 入口不仅是“参数落后”，而是创建门户阶段就可能中断；文档和测试失败提示仍把该菜单当作修复手段，会误导维护者。

**建议：**

- 先完整连接全部引用，再统一应用朝向；或提供一次性 `Initialize(...)`，初始化完成前禁止视觉状态应用。
- `ChangeFacing()` 应能处理未初始化状态，但不能只用空判断掩盖初始化顺序问题。
- 增加 Editor 集成测试：从空场景执行构建，验证 A/B 创建、引用完整性和保存结果。
- 在修复前禁用菜单及批处理入口，而不是只保留“勿运行”的文字约定。

### H-02 — Rebuild 具有覆盖性，且生成内容已落后于当前主场景

**证据：**

- 菜单直接执行 `BuildAll()`：[ProjectBuilder.cs:54-92](../Assets/Editor/ProjectBuilder.cs#L54-L92)。
- 构建会新建 Single 场景并保存到固定 `Level01.unity`：[ProjectBuilder.cs:397-475](../Assets/Editor/ProjectBuilder.cs#L397-L475)。
- Player Prefab 也保存到固定路径：[ProjectBuilder.cs:343-346](../Assets/Editor/ProjectBuilder.cs#L343-L346)。
- Builder 仍使用旧门位置、`openDuration=0.3`、旧相机/门高配置，未同步静态光带、最新 carve 和镜像功能。

**影响：** 完整执行时会覆盖手工维护的主场景和 Prefab；即使 H-01 在保存场景前中断，此前的项目配置、资源和 Prefab 步骤也可能已经执行，并切换到新场景。

**建议：** 二选一：

1. **正式修复构建器**：同步当前场景规范、增加预览/确认/备份、支持非破坏输出路径，并纳入 CI/Editor 测试；
2. **明确退役**：移除或禁用 Rebuild 菜单、批处理方法和测试中的推荐文案，改为维护场景/Prefab 本身。

### H-03 — 朝向应用缺少初始化防护，且存在跨门状态残留

**证据：**

- 公共 `Facing` setter 可直接进入 `ChangeFacing()`，后者没有验证 View、遮罩、输出和 Partner 是否已准备完成。
- B 门朝左分支直接写入另一扇门的父节点缩放：[CaptureDisplayGroup.cs:478-487](../Assets/Scripts/CaptureDisplayGroup.cs#L478-L487)。
- B 门朝右分支只更新自己的节点和 Partner 的 `flipX`，没有对称恢复上述父节点缩放：[CaptureDisplayGroup.cs:467-475](../Assets/Scripts/CaptureDisplayGroup.cs#L467-L475)。

**影响：**

- 初始化、动态重建或缺失节点时可能抛空引用；
- 多次 `B Left → B Right → A/B 切换` 后，视觉结果可能依赖历史操作顺序；
- 一扇门直接修改另一扇门的父节点，破坏组件状态所有权，测试也难以定位来源。

**建议：** 将“朝向 → 完整的本门/对方门视觉状态”改为确定性的纯状态应用：每个分支都显式设置所有相关 `localScale/flipX/flipY/half`，避免只设置当前分支关心的字段；跨门状态由 `PortalPair` 或专用 View 协调器统一写入。

### H-04 — 每帧双门同步图像回读是最主要的性能风险

**证据：**

- `captureInterval=0` 表示每帧捕获：[RegionSnapshotCamera.cs:36-43](../Assets/Scripts/RegionSnapshotCamera.cs#L36-L43)。
- 捕获相机保持 `enabled=true`：[RegionSnapshotCamera.cs:70-75](../Assets/Scripts/RegionSnapshotCamera.cs#L70-L75)。
- 每次捕获又显式调用 `Camera.Render()`，随后 `ReadPixels()` 和 `Apply()`：[RegionSnapshotCamera.cs:196-206](../Assets/Scripts/RegionSnapshotCamera.cs#L196-L206)。
- 静态备用范围 50×35、40 PPU 对应 2000×1400；默认静态 50×50 对应 2000×2000。

**风险：**

1. `ReadPixels` 是同步回读路径，容易造成 CPU/GPU 等待；`Apply` 再把像素上传 GPU。
2. 两台门户相机默认每帧执行，成本随捕获像素数和场景渲染成本增长。
3. URP 自动渲染已启用相机与手动 `Render()` 并存，存在重复提交渲染的风险；**具体渲染次数必须由 Profiler/RenderDoc 验证，不能仅据此断言必然双倍。**

仅按静态 2000×1400 RGB24 原始像素估算，每门每次约 8.4 MB，双门约 16.8 MB；60 次/秒约 1.008 GB/s。该数值只是像素数据量估算，不是实测总带宽或帧耗时。

**建议：**

- 明确只保留一种渲染调度策略，并用 Profiler 验证实际提交次数。
- 评估 URP 合适的 Render Request / AsyncGPUReadback 路径；若坚持同步回读，应降低分辨率、捕获频率并支持脏更新。
- 静态场景可按相机/门/可见内容变化触发捕获；动态场景按目标设备设定预算。
- 将帧时间、主线程等待、GPU 时间、GC 和内存纳入发布验收，而不是只验证 Sprite 非空。

### H-05 — 当前主场景核心镜像路径没有直接回归测试

**证据：**

- 同向门通过 `source.Facing == partner.Facing` 判断，并切换相机/输入镜像：[PortalPair.cs:286-291](../Assets/Scripts/PortalPair.cs#L286-L291)、[PortalPair.cs:369-390](../Assets/Scripts/PortalPair.cs#L369-L390)。

- 主相机已包含 `PlayerCameraMirror`，初始 `mirrorHorizontally: 0`：[Level01.unity:297](../Assets/Scenes/Level01.unity#L297)。
- 当前 4 个测试文件没有针对 `PlayerCameraMirror`、`ToggleMirrorAndInput`、`MirrorPendingCameraPosition` 或投影 `m00` 的直接断言。

**影响：** 最新提交引入的行为正是当前主场景的核心路径；历史 23/23 不能覆盖该功能的奇偶切换、连续传送和禁用恢复。

**必须补充的测试：**

- 同向门连续传送 1、2、3 次，投影镜像和输入反转是否按预期切换；
- 同向与反向门交替传送；

- 传送过程中再次触发碰撞时冷却是否阻止异常重复翻转。

### H-06 — 单轴纹理 Clamp 会破坏输出 Sprite 的世界尺寸

**证据：**

- 宽、高分别独立限制到 `maxTextureSize`：[RegionSnapshotCamera.cs:148-151](../Assets/Scripts/RegionSnapshotCamera.cs#L148-L151)。
- Sprite PPU 只由 `height / worldHeight` 计算：[RegionSnapshotCamera.cs:181-188](../Assets/Scripts/RegionSnapshotCamera.cs#L181-L188)。

**示例：** 世界范围 100×10、40 PPU、上限 2048 时，期望纹理为 4000×400，实际变为 2048×400；PPU 仍为 40，Sprite 世界宽度变成 51.2，而不是 100。

**影响：** 当只有一个轴超限时，捕获画面比例、半屏位置和“1:1 世界范围”约定可能同时失真。

**建议：** 使用同一个等比缩放系数同时限制两轴，并由实际缩放后的像素密度创建 Sprite；若产品策略就是非等比降采样，则必须分别按宽/高计算变换，而不能只按高度。另应校验 `maxTextureSize`、`pixelsPerUnit` 和世界宽高的有效范围。

### H-07 — `carveTerrain` 从 false 恢复 true 时存在开关缺陷

**证据：** [PortalPair.cs:127-142](../Assets/Scripts/PortalPair.cs#L127-L142)。

`carveTerrain=true` 时，只有 carver 为空或宽度参数变化才处理；已有 carver 且参数不变时，没有设置 `enabled=true`。false 分支则会将其禁用。

**影响：** `true → false → true` 且参数未变时，组件保持禁用，地形开洞不再更新。文档已经记录此项，本次回到源码确认成立。

**建议：** 将开关和参数应用集中为幂等方法，每次 true 都明确同步 enabled 状态；增加 `false → true → false` 测试，并同时断言旧洞恢复、新洞生成和 CompositeCollider2D 重建。

### H-08 — PortalHintBeam 在 Player 构建中的保留缺少证据

**证据：**

- 运行时通过 `Shader.Find("Hidden/Platformer/PortalHintBeam")` 获取 Shader：[CaptureDisplayGroup.cs:611-628](../Assets/Scripts/CaptureDisplayGroup.cs#L611-L628)。
- Graphics 的 Always Included Shaders 未列出该 Shader：[GraphicsSettings.asset:29-37](../ProjectSettings/GraphicsSettings.asset#L29-L37)。
- 当前未见场景材质资产对该 Shader 的明确引用。

**影响：** 在 Player 构建剥离条件下，光带 Shader 可能不被打包；编辑器 PlayMode 正常不能证明构建正常。

**建议：** 使用被场景/Prefab 引用的材质资产，或明确加入 Always Included Shaders/合适的最小构建引用；增加 Player 构建烟雾测试并检查光带实际渲染。未构建前只能标记为风险，不能写成已发生剥离。

## 6. P2 详细发现

### H-09 — 光带材质初始化不是幂等操作

- `Awake` 和 `Start` 分别调用 `EnsureHint()`：[CaptureDisplayGroup.cs:355-360](../Assets/Scripts/CaptureDisplayGroup.cs#L355-L360)、[CaptureDisplayGroup.cs:410-415](../Assets/Scripts/CaptureDisplayGroup.cs#L410-L415)。

在光带和 Shader 均存在的正常 Play 生命周期中，第一次材质会失去引用且未显式销毁。属于资源管理缺陷，本次未实测内存增长量。

**建议：** 已存在材质时只更新参数；把创建、获取、销毁统一到一个所有者，并增加重复启用/场景重载测试。

### H-10 — RegionSnapshotCamera 禁用路径不完整

[RegionSnapshotCamera.cs:231-239](../Assets/Scripts/RegionSnapshotCamera.cs#L231-L239) 只在 `OnDestroy` 停用捕获相机并释放目标，没有对应 `OnDisable`。

若组件单独禁用而 GameObject 仍激活，已启用的专用相机可能继续参与 URP 渲染，RenderTexture/Texture2D 也继续保留。

**建议：** 明确 OnEnable/OnDisable/OnDestroy 的资源所有权和对称行为；禁用组件时停止捕获相机，是否立即释放纹理则按内存与重建成本策略决定。

### H-11 — 残余地形碰撞没有继承物理材质

[PortalTerrainCarver.cs:264-273](../Assets/Scripts/PortalTerrainCarver.cs#L264-L273) 新建 `PolygonCollider2D` 后只写入路径，没有复制原地形 `sharedMaterial`。

**影响：** 原地形配置摩擦/弹性材质时，切割后的残余边缘物理表现可能与未切割区域不同。

**建议：** 从实际地形碰撞源继承材质，并补充“开洞前后残余区域材质一致”的测试。

### H-12 — 连续传送的旋转契约不完整

[PortalPair.cs:327-338](../Assets/Scripts/PortalPair.cs#L327-L338) 注释明确假设“玩家进门时是竖直的”，出口角只由出口门角度减入口门角度得到。

**条件性风险：** 玩家上一次传送后仍在回正，又连续进入下一门时，当前显示角不一定为 0；忽略当前角可能产生跳变或错误叠加。

另外，`sameFacing` 只比较枚举，不比较 Transform 实际旋转。它可能是有意的“门类型”语义，也可能与实际朝向概念混用，需要明确设计契约。

**建议：** 用连续传送且未回正的用例确定预期数学关系；将“逻辑朝向”“Transform 旋转”“是否需要镜像”拆成明确概念，避免相互推断。

### H-13 — Respawn 没有定义完整的瞬态状态重置

[PlayerController2D.cs:381-389](../Assets/Scripts/PlayerController2D.cs#L381-L389) 只重置速度、位置、跳跃中状态和回正状态，没有显式清理 `_moveInput`、`_jumpBufferCounter`、`_coyoteCounter`。

**影响：** 重生后可能延续旧跳跃缓冲或土狼时间；持续水平输入是否保留则需要产品定义，不能一概视为错误。

**建议：** 明确“重生后哪些输入保留”；至少清理不应跨生命周期的跳跃缓冲/土狼状态，并添加按住跳跃或移动坠落后的测试。

### H-14 — 非 1 gravityScale 时下落重力计算不一致

- 起跳速度使用 `Physics2D.gravity.y * _rb.gravityScale`：[PlayerController2D.cs:339-347](../Assets/Scripts/PlayerController2D.cs#L339-L347)。
- 额外下落重力只使用 `Physics2D.gravity.y`：[PlayerController2D.cs:356-362](../Assets/Scripts/PlayerController2D.cs#L356-L362)。

当前 Prefab 的 gravityScale 为 1，因此主场景不触发；非 1 缩放时，`fallGravityMultiplier` 的实际效果会偏离统一定义。零重力时起跳回退到 9.81 也应确认是否为设计要求。

**建议：** 统一有效重力计算，并补充 gravityScale 为 0、0.5、2 的参数化测试。

## 10. 项目值得保留的优点

1. **程序集边界清楚**：Runtime、Editor、PlayTests 分离合理。
2. **玩家物理与显示分离**：胶囊保持物理稳定，Visual 负责传送旋转和回正，方向正确。
3. **传送坐标变换较集中**：出口位置、切线偏移和速度变换都基于入口/出口局部坐标，而非世界 Y 的硬编码。
4. **碰撞触发设计有针对性**：只接受玩家 Center Point，身体胶囊通过层排除避免薄门碰撞箱阻挡。
5. **相机延迟映射有时序意识**：pending relative matrix 避免在物理回调中立即修改相机造成顺序问题。
6. **投影镜像避免重复取反**：每帧先 ResetProjectionMatrix，再按状态翻转 `m00`，这一基本策略合理。
7. **捕获资源有复用意识**：尺寸不变时复用纹理，销毁时释放主要 RT/Texture/Sprite。
8. **地形切割具有恢复机制**：旧洞恢复、稳定排序、面积判断和 Composite 重建顺序较完整。
9. **测试不是空壳**：覆盖真实物理、传送、门洞和 Tilemap 行为，能防住一部分核心回归。
10. **文档主动记录限制**：像素遮罩、捕获性能、Shader 构建和 Rebuild 落后等风险并非完全隐藏；本报告已回到源码复核，而不是直接照抄。

## 11. 分阶段整改建议

### 第一阶段：先消除工作成果破坏风险

1. 禁用或修复 Rebuild / Rebuild + Preview 入口。
2. 修复 H-01 初始化顺序，并为 Rebuild 增加 Editor 测试。
3. 对任何覆盖主场景/Prefab 的操作增加明确确认、备份或非破坏输出路径。
4. 更新测试和文档中“运行 Rebuild 修复”的提示。

**验收标准：** 从空场景构建不会空引用；失败不会留下半修改主场景；旧场景不会被无确认覆盖。

### 第二阶段：修复核心正确性并补齐最新功能回归

1. 修复 `carveTerrain` 开关并补 `false → true → false` 测试。
2. 重构 `ChangeFacing` 为完整、幂等、无历史依赖的视觉状态应用。
3. 明确连续传送时玩家当前角、门角和镜像的数学契约。
4. 添加同向/反向门连续传送、投影、输入和相机位置测试。
5. 修复单轴纹理 Clamp 的世界比例问题。

**验收标准：** 状态只由当前配置决定，不由此前切换顺序决定；连续奇偶次传送结果可预测；单轴受限时输出世界尺寸符合明确策略。

### 第三阶段：建立渲染与发布保障

1. 用 Profiler/RenderDoc 确认 Portal Camera 的真实渲染次数和同步等待。
2. 确定异步回读或降频/降分辨率/脏更新方案。
3. 做目标平台 Player 构建，验证 PortalHintBeam 和 Portal View 实际效果。
4. 建立至少一套像素级基准测试或人工视觉验收流程。
5. 对反复加载/卸载场景、禁用/启用组件做内存和资源数量检查。

**验收标准：** 目标设备有明确帧时间和内存预算数据；Player 中光带/遮罩/镜像均有证据；场景反复进入无持续资源增长。

### 第四阶段：降低长期维护成本

1. 将 `CaptureDisplayGroup` 拆成 View Rig、开门/遮罩、Hint/Particle、碰撞转发等较小职责。
2. 将 `ProjectBuilder` 的资源生成、场景生成、校验和预览分离；若退役则删除无效路径。
3. 修复测试全局状态和全局查找，减少固定时间等待。
4. 统一 Outline 参数刷新和 Tile 元数据规则。
5. 明确 `l2.unity` 的归档/维护状态。
6. 更新 README、PROJECT、DEVELOPMENT 的场景值、URP 版本和测试基线。

## 13. 最终结论

这个项目不是“整体失控”的代码库：**核心想法清晰，局部实现有较强针对性，已经有可运行的原型结构、真实 PlayMode 测试和较完整的限制文档。**

但当前健康度的主要短板也很明确：

- **编辑器工具链不可信**，Rebuild 既有空引用路径又有覆盖风险；
- **渲染捕获路径成本高且缺少实测预算**；
- **跨门视觉状态和生命周期管理不够幂等**；
- **最新同向门镜像恰好缺少直接测试**；
- **历史测试通过被文档写成了当前状态，场景与文档也发生漂移**。

因此建议将项目状态定义为：**“原型可继续开发，生产化前必须完成 P0/P1 整改和发布验证。”** 在上述事项完成前，不建议仅凭历史 23/23 结果认定项目整体健康或可直接发布。
