# Unity 2D Portal 优化建议与优化计划

- **适用基线**：`0f6ee18f9025a70094a2d8b03fc9ad472e4af0b0`
- **依据文档**：[代码健康度审查报告](代码健康度审查报告.md)
- **计划性质**：基于静态审查形成的实施建议，尚未执行代码修改、Unity 测试、Profiler 或 Player 构建
- **核心原则**：先保证不破坏工作成果，再修核心行为；先建立回归和性能基线，再做渲染优化与结构拆分

---

## 1. 优化目标

### 1.1 必须达到

1. **工程安全**：任何菜单、批处理和预览入口都不能无确认覆盖主场景或 Prefab，失败时不能留下半完成状态。
2. **行为确定**：相同场景和输入必须得到相同的传送、镜像、遮罩和开洞结果，不能依赖此前的切换顺序。
3. **最新功能可回归**：同向门镜像、输入反转、连续传送和相机相对映射必须有直接测试。
4. **渲染成本可解释**：明确每台 Portal Camera 的实际渲染次数、回读成本、纹理尺寸和捕获频率。
5. **生命周期完整**：初始化、禁用、启用、销毁、场景重载和退出 PlayMode 都有明确的资源与状态所有权。
6. **发布结果有证据**：目标平台 Player 中光带、遮罩、传送、镜像和性能均经过验证。

### 1.2 可以延后

- 为“代码更漂亮”而进行全面重写；
- 与当前问题无关的 UI、输入系统或包版本升级；
- 在没有 Profiler 证据时替换整个 URP 捕获架构；
- 过早引入复杂配置框架、事件总线、依赖注入或通用插件化系统；
- 对明确归档的旧场景继续投入兼容成本。

## 2. 推荐实施顺序

```text
建立当前基线
    ↓
封锁危险入口 / 修复确定性缺陷
    ↓
补齐镜像、连续传送、开洞和构建回归
    ↓
测量捕获渲染与回读瓶颈
    ↓
优化捕获调度、纹理预算和资源生命周期
    ↓
完成目标平台视觉与性能验收
    ↓
在测试保护下拆分大类、清理旧场景和文档
```

**不要反过来执行。** 如果先拆 `CaptureDisplayGroup` 或先改异步回读，而镜像和连续传送没有测试，行为回归会很难定位。

## 4. 分项优化建议

## 4.1 工程安全：先处理 Rebuild

### 短期建议

- 在入口修复前，禁用 `Rebuild Level + Prefabs` 和 `Rebuild + Render Preview`，不要只依赖文档中的“勿运行”。
- 暂停测试失败提示中“运行 Rebuild 修复”的引导，改为检查 Layer、Prefab、Scene 和资源引用。
- 保留当前 `Level01.unity` 和 Player Prefab 的独立备份或版本控制确认点。

### 长期方案二选一

#### 方案 A：主场景继续手工维护，退役 Builder

**适用情况：** 当前场景包含大量手工调优，自动生成不是实际工作流。

- 移除或禁用重建入口；
- 保留只读、非破坏的 Validate；
- 将文档中的场景维护方式设为唯一事实来源；
- 不再投入成本追赶所有手工视觉参数。

**优点：** 改动最小，立即消除两套场景来源。**代价：** 后续新关卡需要复制/Prefab 化或另建安全生成流程。

#### 方案 B：正式修复 Builder

**适用情况：** 团队确实需要从空项目重复生成关卡。

- 先连接完整引用，再应用 `Facing`；
- 初始化期间禁止 `ChangeFacing()` 访问未准备对象；
- 默认输出到新场景/临时 Prefab 路径，验证通过后再由用户显式替换；
- 增加覆盖确认、备份和失败回滚；
- 同步当前动态捕获、carve、光带、粒子和镜像配置；
- 用 Editor 集成测试验证从空场景生成到保存的完整链路。

**建议选择：** 如果没有明确的自动生成需求，优先方案 A；不要维护一个“看似可用但实际落后”的生成器。

### 验收标准

- 不存在可无确认覆盖主场景的公开菜单或批处理入口；
- 新组件初始化不会进入空引用路径；
- 失败不会留下相机、资源或场景半修改状态；
- 文档、测试提示和实际工作流一致。

## 4.2 核心正确性：让状态只由当前配置决定

### A. 重构朝向状态应用

针对 H-03：

1. 将“数据初始化”和“视觉状态应用”分开。
2. 用一个入口完整计算并应用本门及对方门的 `localScale`、`flipX`、`flipY` 和输出半屏。
3. 每个分支都恢复所有受控字段，不能只设置当前分支需要的字段。
4. 禁止 B 门直接改另一扇门的父节点；跨门状态交给 `PortalPair` 或专用 View 协调器。
5. 缺失 Partner/View 时保持安全状态并给出可定位错误，不继续写空引用。

**专项测试：** A/B 各 Left/Right、重复设置相同值、Left→Right→Left、缺失 Partner、缺失 Mask、运行时重绑定。

### B. 修复 carve 开关

针对 H-07：

- 用一个幂等方法统一同步 `carveTerrain`、carver enabled、宽度、前缘边距和门状态；
- true 分支无论参数是否变化，都必须保证组件处于预期 enabled 状态；
- false 时恢复全部旧洞，true 时按当前门位置重新开洞；
- 避免在 `Update` 中散落多个半套状态同步逻辑。

**专项测试：** `true→false→true→false`，参数变/不变分别覆盖，并断言 Tile ColliderType、Composite 路径和残余碰撞对象数量。

### C. 明确连续传送旋转契约

针对 H-12：

- 明确出口角是“相对当前玩家显示角叠加”还是“重置为门间角度差”；
- 用数学公式和测试固定预期，不能只靠“进门时竖直”的注释假设；
- 区分逻辑 Facing、Transform 旋转和镜像语义；
- 明确回正过程中再次传送时，旧回正动画如何取消或重定向。

### 验收标准

- 多次切换后的最终视觉状态与直接设置到该状态完全一致；
- 开洞开关可重复，旧洞不残留；
- 连续传送结果与传送次数和当前状态符合明确公式，不出现偶发角度跳变。

## 4.3 镜像与相机：先补测试，再改实现

针对 H-05、H-20：

### 必补测试

1. 同向门传送 1、2、3 次，验证投影 `m00`、水平输入和相机位置的奇偶变化。
2. 同向与反向门交替传送。
3. 镜像状态下跳跃、左右移动、回正和前瞻。
4. 传送冷却期间重复碰撞，不得额外翻转。
5. `PlayerCameraMirror.OnDisable`、场景卸载和退出 PlayMode 后恢复状态。
6. 手动输入与键盘输入分别验证，避免测试只覆盖其中一种。
7. 多相机/多玩家或运行时重绑定若属于支持范围，必须显式测试；否则在文档中声明不支持。

### 实现建议

- 玩家和相机使用显式引用，避免全局 `FindObjectOfType` 作为常规绑定方式；
- 输入反转由单一所有者管理，保存进入功能前的状态，退出时恢复而不是强制写 false；
- VisualRoot 可替换时重新解析缓存，不可替换时明确限制；
- 保持“先 ResetProjectionMatrix，再按当前状态设置矩阵”的防重复取反策略。

### 验收标准

- 镜像状态、输入状态和相机状态始终一致；
- 禁用组件不会覆盖其他系统的输入状态；
- 奇偶次连续传送均有自动化断言。

## 4.4 渲染性能：先测量，再按瓶颈优化

针对 H-04、H-06：

### 第一步：建立性能基线

在同一 Scene、同一 Game View 尺寸、同一目标设备上记录：

- 主线程帧时间及 `Camera.Render`、`ReadPixels`、`Texture2D.Apply` 的耗时；
- Render Thread / GPU 时间；
- 每台 Portal Camera 每帧实际渲染次数；
- RT/Texture2D 的宽、高、格式和数量；
- GC.Alloc、总内存及反复加载场景后的变化；
- 静态、动态、传送强制刷新三种情况。

不要先假设“一定双倍渲染”或“异步化一定更快”，以 Profiler/RenderDoc 和真机结果为准。

### 第二步：消除明确浪费

1. **单一渲染调度**：明确由 URP 自动渲染还是捕获管理器主动请求，避免两套调度同时存在。
2. **尺寸不变时复用**：继续复用 RT、Texture2D、完整 Sprite 和半屏 Sprite，避免每帧重建对象。
3. **等比限制纹理**：两轴使用同一缩放系数，确保 Sprite 世界尺寸不被单轴 Clamp 破坏。
4. **无效场景不捕获**：门未配对、输出不可见、组件禁用或图形设备不支持时跳过。
5. **静态内容脏更新**：源相机、门、捕获范围或可见场景未变化时复用上一帧。
6. **传送强制刷新保留**：将传送后的捕获设为明确的 dirty 原因，避免缓存影响正确性。

### 第三步：按测量结果选择进一步优化

| 瓶颈 | 优先方案 | 注意事项 |
|---|---|---|
| 双门每帧都渲染 | 降频、可见性判断、双门错峰调度 | 必须保留传送帧强制同步 |
| 高分辨率像素成本 | 等比降低捕获 PPU、限制纹理预算 | 同时验证遮罩边缘和文字/细节可读性 |
| 主线程阻塞在 ReadPixels | 评估 AsyncGPUReadback | 检查平台支持、延迟帧和资源生命周期 |
| 场景重复渲染成本 | 减少捕获频率或优化捕获 Culling Mask | 不得意外捕获 Portal View 形成递归 |
| 频繁尺寸变化 | 稳定尺寸档位，减少 RT/Texture 重建 | 防止尺寸抖动引起反复分配 |

### 推荐的捕获优先级

```text
传送/门状态变化：必须立即刷新
    >
玩家或源相机明显变化：按目标频率刷新
    >
门在视野外或完全静止：降低频率或复用缓存
```

### 不建议

- 只靠提高 `maxTextureSize` 解决比例或清晰度问题；
- 未测量就同时改渲染调度、纹理格式、分辨率和异步回读；
- 为追求帧率取消所有传送强制刷新；
- 将异步回读结果写回已销毁的 Texture/Sprite。

### 验收标准

- 有优化前后同场景、同设备的对比数据；
- 捕获画面没有比例变化、明显过期或传送帧错位；
- 无双倍调度、无持续纹理增长、无每帧不必要的 Sprite 分配；
- 目标帧率与画质预算由项目实际设备确定，不使用未经验证的通用数值。

## 4.5 资源生命周期：让所有创建操作幂等、可释放

针对 H-09、H-10、H-11：

### CaptureDisplayGroup

- `_beamMaterial` 已存在时只更新参数，不重复 `new Material`；
- 明确 Sprite、Material、静态共享 Particle Material 的所有者；
- `OnDestroy` 释放本组件实际拥有的资源，避免误销毁共享资产；
- 初始化失败时也能清理已经创建的临时资源。

### RegionSnapshotCamera

- 建立对称的 `OnEnable` / `OnDisable` / `OnDestroy` 行为；
- 禁用组件时停止专用捕获相机；
- 明确禁用时是保留纹理以便快速恢复，还是释放纹理以降低内存；
- 异步回读若引入，必须在回调中验证组件、纹理和请求代次仍有效。

### PortalTerrainCarver

- 残余 PolygonCollider2D 继承原地形物理材质；
- 门移动/旋转造成反复重建时记录 GC 和物理重建成本；
- 只有矩形或地形内容变化时才刷新；
- 若支持运行时外部修改 Tilemap，提供显式通知/刷新接口，不建议每帧全图扫描。

### 验收测试

- 重复进入/退出 PlayMode；
- 同一场景反复加载/卸载；
- 组件重复禁用/启用；
- 门持续移动和旋转；
- 对比 Texture、Sprite、Material、Collider 数量与内存是否回到稳定水平。

## 4.6 玩家、物理和边界状态

针对 H-13、H-14、H-22：

1. **重生状态**：明确水平输入是否保留，清理不应跨生命周期的跳跃缓冲、土狼时间和旧回正状态。
2. **统一有效重力**：起跳和额外下落都基于 `Physics2D.gravity * Rigidbody2D.gravityScale`。
3. **零重力设计**：明确零重力时是否允许跳跃；若允许，解释回退重力 9.81 的设计原因。
4. **换玩家**：保存旧玩家原始 `excludeLayers`，解绑时恢复；新玩家绑定只修改本系统负责的位。
5. **参数校验**：在 Inspector 和公共 API 边界约束负尺寸、非法 PPU、零/非有限数值。

### 必补测试

- 按住跳跃或移动时坠落重生；
- 回正过程中重生/再次传送；
- gravityScale 为 0、0.5、1、2；
- 玩家 A→B→A 切换后的碰撞层恢复；
- 零重力下跳跃行为与设计一致。

## 4.7 测试体系：从“有用例”提升为“证据可靠”

针对 H-16 及全部验证缺口：

### 测试基础设施

- SetUp 保存、TearDown 恢复 `Physics2D.gravity` 等全局状态；
- additive 加载后，只在目标 Scene 的 Root/对象内查找，不使用跨场景全局 Find；
- 用“等待条件成立 + 超时失败”替代固定 `WaitForSeconds`；
- 将纯数学/状态逻辑拆成可单测的函数，减少所有验证都依赖真实帧和渲染；
- 明确 Editor PlayMode 与 Standalone PlayMode 的支持范围；
- 无图形设备跳过渲染测试时，结果中必须清楚标记 skipped，不能视为视觉通过。

### 建议测试层次

| 层次 | 内容 | 价值 |
|---|---|---|
| 纯逻辑测试 | 传送向量、角度、镜像奇偶、纹理等比缩放、开洞矩形 | 快速、稳定、易定位 |
| PlayMode 集成 | 玩家物理、碰撞、门动画、相机、开洞和生命周期 | 验证 Unity 组件协作 |
| 像素/视觉测试 | 半屏、SpriteMask、光带、镜像后的最终画面 | 覆盖结构断言无法发现的问题 |
| 构建烟雾测试 | Player 启动、传送、Shader、输入和资源 | 防止编辑器与 Player 差异 |
| 性能测试 | 双门捕获、最大尺寸、移动门、场景反复加载 | 防止帧时间和内存回归 |

### 当前历史结果处理

- 先在与当前 HEAD 一致的代码上重新执行完整 23 个测试；
- 结果记录提交号、Unity 版本、平台、图形设备、时间和跳过项；
- 文档只引用对应基线的结果，不写成永久“当前通过”。

## 4.8 可维护性：最后做小步结构优化

### CaptureDisplayGroup 拆分方向

在行为测试稳定后，可逐步拆为：

- **PortalViewRig**：解析和校验 View、Mask、Output 引用；
- **PortalViewComposer**：完整/半屏 Sprite、裁剪位置、遮罩和显示状态；
- **PortalOpenAnimation**：开门进度和动画状态；
- **PortalHintController**：光带、粒子和材质生命周期；
- **CaptureDisplayGroup**：仅保留配对、协调和碰撞转发，或进一步缩小门面职责。

每一步只迁移一个职责，迁移前后运行同一组测试，不同时改变视觉算法。

### TilemapOutline

- 用显式 Tile 类型/元数据替代 `Dark`、`Slope` 名称约定；
- 参数刷新和资源创建分离；
- 斜坡和普通边共享线宽策略；

## 6. 最小优化包

如果希望先用最少改动获得最大收益，建议只执行以下六项：

1. **禁用或修复 Rebuild**，消除工作成果破坏风险；
2. **修复 carve 开关**，补 false→true 测试；
3. **修复 ChangeFacing 跨门状态**，补重复切换测试；
4. **补同向门连续传送与镜像测试**；
5. **测量并优化双门捕获**，先消除重复调度和不必要捕获；
6. **做一次 Player 构建与视觉验收**，确认 Shader、Mask 和镜像。

这六项完成后，再评估资源生命周期、玩家边界条件和大类拆分，不建议一开始全面重写。

## 8. 执行风险控制

- **每个优化主题独立变更**：不要把 Builder、传送数学、渲染调度和类拆分放在同一次修改中。
- **先测试后重构**：没有回归保护的路径，先补表征测试，再移动代码。
- **场景修改单独审查**：Unity YAML diff 大，避免代码与大量场景序列化变化混杂。
- **性能优化一次只改一个主变量**：渲染次数、分辨率、回读方式不要同时改变，否则无法归因。
- **保留回退点**：捕获架构和视觉状态修改应可独立回退。
- **不把风险写成已修复**：静态审查只能指导实施，最终结论必须由测试、构建、Profiler 和视觉验收更新。

## 9. 最终建议

本项目不需要推倒重来。最合理的路线是：

> **保留现有玩家物理、传送坐标变换和测试基础；先退役/修复危险工具，收敛跨组件状态，再围绕捕获调度与资源生命周期做可测量优化，最后才拆分大类。**

完成“最小优化包”后，项目的主要风险会明显下降；完成 M0—M4 后，才具备较可信的生产化评估基础。M5 的结构优化应以降低维护成本为目标，而不是以改变架构形态为目标。
